## New

| # | Date | Decision |
|---|---|---|
| D7 | 2026-08-31 | **Phrase WAVs are 16-bit signed PCM, and `tools/wav_to_phrases.py` is the only conversion path.** The three recorded WAVs in `Messages/` were 32-bit IEEE float (WAV format tag 3). Fed to `i2s_write()` configured for `I2S_BITS_PER_SAMPLE_16BIT` that plays as full-scale noise, costs double the flash, and Python's `wave` module cannot even open it -- which would also have broken the mock server. `Messages/*.wav` stays the recorded source of truth; the converter owns format, trimming, and level. |
| D8 | 2026-08-31 | **`firmware/src/phrases.h` is generated and gitignored.** 393 KB of C source for 3 phrases; regenerate with `python tools/wav_to_phrases.py --emit-header`. Committing it would make every phrase change a giant diff. |
| D9 | 2026-08-31 | **`platformio.ini` pins `espressif32@6.5.0` (Arduino-ESP32 core 2.0.14).** The I2S code in the software brief is the legacy `i2s_config_t` / `i2s_write()` driver. Core 3.x replaces it with `I2SClass`, so an unpinned platform would silently break the audio path on whoever installs next. Revisit only if we want the new API deliberately. |
| D10 | 2026-08-31 | **HTTPS: plain HTTP to the mock, TLS to OpenRouter, `setInsecure()` for cert validation.** Settles the question raised on 08-31. The mock stays plain HTTP for all four weeks -- deliberate, so that when TLS breaks we know it is TLS, and it is the demo-day fallback. But OpenRouter serves no `http://` endpoint, so TLS is not optional for the real leg. There is no certificate for us to obtain: we are the client, the cert is OpenRouter's. We skip *validating* it via `client.setInsecure()`, which is one line and removes the certificate-expiry risk on demo day. TLS lands in week 2 as an isolated step because `WiFiClientSecure` wants 40-50 KB of internal heap alongside the camera framebuffer -- it is a memory exercise, not a security checkbox, and deferring it hides that risk until week 4. Named as a known limitation in the writeup. |
| D11 | 2026-08-31 | **The mock validates uploads and can be made to fail on demand.** It base64-decodes every upload and checks SOI/EOI markers and padding, because a streaming base64 encoder that drops its tail is the likeliest firmware bug and is invisible from the device end. `POST /mock/scenario` switches between `ok, notext, http500, timeout, garbage, empty` so the state machine's failure paths are testable without unplugging anything. |
| D12 | 2026-08-31 | **The eval scorer treats number words and digits as the same fact.** "three times a day" and "3 times a day" are the same dose and the model correctly transcribes whichever is printed; without normalising, every run drowns in false failures. Month names normalise too, so "12 September" and "12/09" score alike. |
| D14 | 2026-08-31 | **CORRECTS D5 -- OpenRouter has no `/audio/speech` endpoint and no `response_format: pcm`.** Verified against the live API: `openai/gpt-4o-mini-tts-2025-12-15` returns 400 "Model does not exist", and so does every other TTS name tried; `/audio/speech` rejects even models that do exist. Of 396 models, only 4 output audio -- two Lyria (music, not speech) and `openai/gpt-audio` / `openai/gpt-audio-mini`. The working path is **`openai/gpt-audio-mini` on `/chat/completions` with `stream: true`** (audio output is refused without it), `modalities: ["text","audio"]`, `audio: {voice, format: "pcm16"}`. Audio arrives as **base64 inside SSE `delta.audio.data` chunks**, not as a raw body. Measured: 13 chunks, 232,800 bytes, first audio byte at 1.60 s, stream complete at 2.28 s. |
| D15 | 2026-08-31 | **TTS output is 24 kHz, 16-bit, mono, headerless PCM -- confirmed, closing the day-1 unknown.** 116,400 samples for a 73-character utterance is 4.85 s at 24 kHz; natural speech runs 14-16 chars/s, so 4.6-5.2 s is expected. 16 kHz would imply 7.28 s (far too slow) and 44.1/48 kHz under 2.7 s (far too fast). Matches the recorded phrase WAVs and `TTS_SAMPLE_RATE` in config.h -- no firmware change needed. |
| D16 | 2026-08-31 | **Vision model: `google/gemini-3.5-flash-lite` is the recommended swap from `gemini-3-flash-preview`, pending the 20-photo eval.** Measured on the same image: 1.54 s vs 2.97 s (**1.4 s faster**) and $0.45 vs $0.71 per 1000 presses (**37% cheaper**), with identical accuracy (5/5 numbers on a clean label, and all four candidates degrade equally on a hard one). The 1.4 s saving takes the cloud round trip from ~5.05 s to ~3.14 s, which is real headroom under the 6 s target once device capture and upload are added. `gemini-3.1-flash-lite` is a close second at $0.35. **Do not switch on this evidence alone** -- confirm on the real eval set. |
| D17 | 2026-08-31 | **Mode A gets an uncertainty-aware prompt, and the device must speak the doubt.** On a deliberately degraded label (low contrast, curved, rotated, slightly blurred) EVERY candidate model confidently invented numbers rather than abstaining: quantity 56 read as 60 by all four, expiry dates returned as `09/31/26` (a date that does not exist), `00/00/00`, and `03/2026`; one model read "1 tablet" as "I tablet"; one fabricated an entire line ("Dist by: Sandoz Inc., Princeton") that appears nowhere in the image. For a device that reads medicine labels aloud to someone who cannot verify the result, this is the most dangerous failure mode in the project. Adding "never guess a character you cannot clearly see; mark unclear digits `[?]`; write UNCLEAR after any important number you cannot read with certainty" produced 6 uncertainty markers on the same image. It does NOT make the numbers right -- it makes the device honest. **Requires a new offline phrase** ("I am not certain of this. Try more light, or move closer.") and state-machine handling when UNCLEAR appears near a number. |
| D18 | 2026-08-31 | **Image quality, not model choice, is the accuracy lever -- which promotes two hardware tasks to critical.** All four vision models failed near-identically on a degraded image and all succeeded on a clean one, so no model swap fixes accuracy. What fixes it is upstream: the **lens refocus to 15-25 cm** (currently factory-set near infinity) and the **two diffused LEDs** either side of the lens. Both were framed as polish in the hardware brief; on this evidence they are the primary accuracy mechanism. Worth re-testing JPEG quality above q12 as well -- the hard image compressed to only 8.7 KB. |
| D13 | 2026-08-31 | **`make_phrases.py` must not run until the cloud TTS voice is chosen.** The point of D6 is cloning the voice we actually ship, so generating the remaining 6 phrases first means doing it twice. Ordering: pick voice -> capture a sample with `reference_pipeline.py` -> clone -> generate. |
| D19 | 2026-09-04 | **`reference_pipeline.py` and `config.example.h` moved onto the D14 shape; the mock was already there.** The mock server was reshaped for D14 in commit 566661d but the reference pipeline was not, so it still POSTed `/audio/speech` with `response_format: pcm` and died on `400 Model openai/gpt-4o-mini-tts-2025-12-15 does not exist` -- against the mock *and* the real API. That inverted the rule that the pipeline is ground truth ("if the device disagrees with this script, the device is wrong"). `tts()` now does SSE framing and per-delta base64 decoding with the one-byte sample carry, written the way firmware must write it, and reports time-to-first-audio-byte separately from completion. `config.example.h` and the local `config.h` carried the dead `TTS_MODEL` and no `TTS_AUDIO_FORMAT`, so firmware started from the template would have built the wrong audio path on day one; both now carry the working values plus the request shape in a comment block. **Vision model deliberately left on `gemini-3-flash-preview`** -- D16 says do not switch until the 20-photo eval confirms it. |
